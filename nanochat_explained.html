Nanochat vs. GPT-2: The Evolution

This document visualizes why nanochat represents a 5-year leap in efficiency over the original GPT-2 architecture, enabling the training of LLMs for under $100.

1. The High-Level Comparison

Nanochat is not just a reimplementation; it's a modernization. Every component has been swapped for a more efficient counterpart found in research from 2019-2026.

Feature Original GPT-2 (2019) NanoGPT (2023) Nanochat (2026) Technical "Why" (Deep Dive)
Optimizer Adam (FP32) AdamW (BF16) Muon + AdamW Newton-Schulz iteration maintains matrix spectral radius ≈ 1. This stability allows taking updates with 30x higher energy (LR=0.02) without diverging.
Attention O(N²) Math Flash Attention 2 Flash Attention 3 Utilizes Hopper's asynchronous TMA and warp-specialization to overlap compute with data movement, doubling SRAM throughput over FA2.
Positioning Absolute Absolute Rotary (RoPE) Rotates Q/K pairs in the complex plane. This preserves inner-product decay relative to distance, allowing better length extrapolation than static maps.
Normalization LayerNorm (+Bias) LayerNorm (-Bias) RMSNorm Removing mean-centering saves O(N) ops. Implementation is purely functional (no affine weights), reducing memory bandwidth and param count.
Activation GeLU New GeLU ReLU² Second-order curvature provides smoother gradients than ReLU without the expensive exp/tanh of GeLU. Better loss-per-second at GPT-2 scale.
Shortcut Residual Only Residual Only x0 + Residual Directly blends input embeddings into every layer. This mitigates residual noise washout and gradient vanishing in very deep stacks.
Capacity Standard Standard Value Embeddings Decouples Param Count from FLOPs. Injects facts via V-stream table lookups without increasing the O(d²) cost of matrix projections.

Key Innovation: Value Embeddings
Note the Value Embeddings Table injecting data into the V path. This allows the model to "memorize" more information without making the expensive matrix multiplications (Q, K, V projections) larger. It's "cheap" capacity.

3. The "Muon" Optimizer Effect

The standard AdamW optimizer updates every parameter independently. Muon updates 2D matrices as a whole, forcing updates to be orthogonal. This is implemented in optim.py.

flowchart LR subgraph AdamW ["Standard AdamW"] G1["Gradient"] --> M1["Momentum"] M1 --> S1["Scale by 1/sqrt(v)"] S1 --> U1["Update Weight"] style S1 fill:#f9f,stroke:#333,stroke-width:2px end subgraph Muon ["Muon Optimizer"] G2["Gradient"] --> M2["Momentum"] M2 --> NS["Newton-Schulz Orthogonalization"] NS --> U2["Update Matrix"] style NS fill:#10b981,stroke:#333,stroke-width:4px,color:white end

Why it matters: The Newton-Schulz step cleans up the internal structure of the weight matrices. This allows us to use learning rates (e.g., 0.02) that are ~30x higher than what AdamW can tolerate (0.0006), leading to much faster convergence.

4. Training Logic: Scaling Laws

In scripts/base_train.py, hyperparameters are not guessed; they are calculated.

Hyperparameter Nanochat Logic Result
Training Duration TargetTokens = 10.5 * Params Ensures compute-optimality (Chinchilla-style).
Batch Size BatchSize ∝ Depth^0.383 Larger models get larger batches (Power Laws).
Learning Rate LR ∝ sqrt(BatchSize) Compensates for larger batches with larger steps.
Weight Decay WD ∝ 1 / Width^2 Wider models get stricter regularization.
